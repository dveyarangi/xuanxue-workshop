### Approved breakdown

1. **[native-cabinet-account-session](../tickets/01-0008-native-cabinet-account-session.md) — Ready (alignment); HITL.** One coordinating outcome:
   native Daychi signs in to Cabinet, securely retains/restores its Cabinet-issued
   credential, reads its current Cabinet account, and signs out of that installation
   without ending other clients' sessions. Cabinet web access remains supported.
   This advances the credential row of the accepted migration delta and supplies
   the account-access foundation for later authenticated schedule/reminder work.
   It does not claim that the full migration is complete.

   **Responsible contributors:** Workshop owns the shared agreement and joint
   acceptance; Cabinet's agent/operator owns issuance, bearer validation and web
   regression proof; Daychi's agent/operator owns the native client and its proof.
   Cabinet remains the account/session authority and data owner.

   **Dependencies by activity:** local contract preparation has no dependency on
   public-provider correction, native public-pilot proof or Daychi installation.
   Breakdown approval and minting are complete. Publishing implementation assignments
   requires settled shared definitions, common cases and an accessible immutable
   authority. Each recipient's implementation requires its accepted collaboration
   installation and its operator's authority. Joint native proof additionally
   requires the reachable auth provider and a controlled test account. Cabinet's
   installation is already accepted; Daychi's remains outstanding.

   **Scope:** Cabinet account sign-in, credential restoration/renewal, one existing
   account read, current-user refusal and temporary-failure recovery, and
   installation-scoped sign-out. The existing browser/code-and-PKCE handoff remains
   the provisional baseline. Exact native operations, responses, client/redirect
   binding, token lifecycle and concurrent credential use remain shared decisions;
   this proposal selects no token format or expiry policy.

   **Excluded:** Daychi content-admission replacement, content backend retirement,
   reminder synchronization, protected schedule cutover, gateway implementation,
   new background polling and native server push. Existing content credentials,
   ordinary schedule/cache/selections and OS reminders are compatibility obligations.

   **Acceptance:** both projects implement the same pinned native-session contract;
   a real native runtime completes Cabinet sign-in and account read, restores the
   session after restart, exercises the agreed expiry/renewal behavior, distinguishes
   refusal from temporary failure and recovers; sign-out leaves other installations
   signed in. Cancellation, mismatched/replayed handoffs, unavailable provider and
   interrupted credential persistence have agreed common outcomes and executed
   checks. Cabinet web and Daychi's ordinary/content paths have regression evidence.
   Workshop reviews original-issue reports and reconciles its current records.

### Impact

Load-bearing: this crosses account authority, browser/native transport, credentials
and their lifecycle. Provider and client must share one contract. The proposed
single outcome crosses the full path; two recipient issues would be contributions
to it, not separate horizontal local tickets. It creates a useful account-access
capability without requiring the whole reminder/content migration.

### Hidden edges

Cookie rolling renewal is not a native renewal response. Cabinet's current logout
clears a cookie; its stateless token does not establish per-installation server
revocation. Daychi's existing decoder and storage key belong to a different authority.
The existing native URL handler handles invitations, so callback integration must
preserve those links. Refusal, user blocking, renewal races, cancelled browser flows
and failures during persistence need common outcomes before issue publication.
The content-admission and gateway straw dogs remain bound to their existing
questions; this proposal does not resolve or reopen either deferral.

### Leave alone

Existing queue order, readiness/installation assignments, public pilot issues and
their fixed wire contract; Cabinet web sign-in; Daychi content authority and stored
credentials; ordinary schedule/cache/reminders; deferred gateway and consolidation.

of one broad authentication/content/reminder migration. The narrowed slice is the
breakdown above. Its approval adds this outcome to prepared work without releasing
sibling implementation or finalizing the authentication standard. No further split
