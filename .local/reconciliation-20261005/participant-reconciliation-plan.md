## Expected sequence and observable handoffs

1. **Preparation:** The fixed agreement is consolidated in one maintained
   contract/example record. The source comparison and common checks explain the
   provider/client deltas. A single coordinating outcome is shaped through the
   existing ticket/impact process; no ticket is minted before breakdown approval.
2. **Publication and readiness:** The contract reference becomes readable at an
   exact published revision after the existing commit/push checkpoints. Workshop
   readiness is verified and published; original installation issues receive
   readiness/release evidence. Nothing here replaces their remaining fresh-entry
   or independent-grading proof.
3. **Recipient installation:** Each agent installs and verifies /collaborate under
   its operator and reports in its existing installation issue. Workshop checks
   those criteria, reconciles adoption evidence and acknowledges there. Each
   project's execution readiness is independent of the other's installation.
4. **Application assignments:** Two provider/consumer issues cite the same
   immutable agreement/examples and carry different recipient actions. They may
   be published Planned once the contract is complete and accessible. Their
   execution waits for the respective readiness/onboarding dependencies. Neither
   is a renewed broad inventory request.
5. **Provider and consumer work:** Cabinet implements the additional public read
   and supplies source/check evidence and reproducible provider setup. Daychi can
   implement its reader from the fixed contract/common fixtures independently;
   its actual integration proof also requires the provider to be reachable.
   The entire consumer implementation need not wait for a deployed provider.
6. **Controlled integration:** Cabinet arranges disposable lesson data and
   changes under its operator. Daychi's native runtime reads that exact provider,
   refreshes after the arranged changes and demonstrates failure/recovery. The
   two original issues cross-reference the same scenario, provider revision and
   observations. No third success-report issue is created.
7. **Workshop reconciliation:** Returned evidence feeds the existing comparison
   and record updates as described below, before acceptance acknowledgement.
8. **Outcome closure:** Individual contributions close on their own verified
   criteria. The coordinating outcome closes only after combined native/provider
   evidence, preserved-path checks, current records and its own /verify. Neither
   this closure nor the first-stage goal silently releases later migration work.

Steps 2–4 express existing dependencies, not a new gate that every project waits
for every other project. Contract publication can precede readiness; Planned
application posting can precede verified onboarding; native integration proof
cannot precede an accessible provider. New-cycle and operator checkpoints remain.

## How actual reconciliation follows a report

Workshop's next session entry or resumed reconciliation discovers relevant
incoming requests and outgoing-assignment conversations in all issue states.
Filtering only `project:workshop` would miss reports in Cabinet/Daychi assignments.
No unattended watcher is implied. An unchanged last Workshop response needs no
repeat acknowledgement.

For a provider report, Workshop compares the reported source/check/runtime
revision against the assignment's fixed contract and checks each required outcome.
Source inspection can substantiate implementation; an observed request adds
running-provider evidence; neither establishes native consumption. If complete,
the comparison records provider implementation/evidence and leaves the native
consumer pending. If evidence is missing or inconsistent, the original Cabinet
issue receives the specific unresolved requirement, without false acceptance.

For a consumer report, Workshop matches the native request/result and arranged
lesson changes to the provider revision and the same contract. It checks that
the native path really used Cabinet, respects window/privacy/identity semantics,
and preserves ordinary Daychi state. It accepts complete inspectable evidence;
re-execution is needed only to resolve a gap or contradiction. Two independent
green test reports alone do not prove that the applications connected.

The record changes have distinct homes:

| Record | Result it would describe after verified evidence |
|---|---|
| `docs/current-system.md` | Provider/client modules and revisions actually inspected, checks actually executed/reported, native connection actually demonstrated, environment/deployment limits. Provider-only evidence leaves native integration explicitly pending. |
| `docs/boundaries.md` and the common contract record | Accepted promises and compatibility; unchanged when implementation simply fulfils them. A genuine new shared decision is aligned in its own scope. |
| `docs/migration-changes.md` | Remaining delta and accepted completion status; ordinary source cutover/accounts/reminders remain separate. No blanket migration-complete claim. |
| Current reconciliation report/local outcome | Updated comparison, specific unresolved evidence and the resumption point; original issue links retain the discussion rather than copying an acknowledgement ledger. |
| Project instruction summaries | Observed provider/consumer changes with canonical links, separately labelled remaining targets. Each project updates its own instructions; Workshop supplies a complete summary block when issuing an instruction update. |

Workshop rereads the original issue for intervening evidence before its response
or closure. When necessary records have changed, acknowledgement references their
published revision. If publication awaits operator approval, review can be
recorded as pending publication, but acceptance is not falsely claimed. When no
boundary record changes, acknowledgement says so explicitly. Workshop reads back
its response and state change. The same closed issue is still reviewed if it
contains a new unaccepted report.

## Counterexamples walked through

| Situation | Disposition under the existing process |
|---|---|
| Cabinet reports only compilation/unit success | Source evidence is considered, but missing route/privacy/runtime criteria remain in the Cabinet issue. Native integration remains unproved. |
| Both agents have green mock tests; native cannot reach provider | The combined outcome stays incomplete. Actual URL/runtime/error evidence identifies the provider setup or consumer network/configuration obstacle; the responsible original issue carries follow-up. |
| Daychi shows Cabinet-like rows through HTML fallback | Reject that as Cabinet integration evidence; the ordinary flow stays preserved but cannot masquerade as the pilot provider. |
| Daychi changes only its display, leaving the old transferred lesson behind | Check the already-agreed refresh/identity case; request the missing correction in its issue without reopening the refresh decision. |
| A project has already closed its issue with an incomplete report | Review the report and record the remaining evidence in that issue; closed state is not acceptance. |
| Source/provider evidence is complete, deployment is not reported | Record the supported implementation/running-environment claim only; do not infer production deployment. |
| A record patch is prepared but not published | Keep acknowledgement/publication pending; obtain the existing concrete commit/push approval instead of claiming reconciliation published. |
| Workshop asked for missing proof; no new response arrived | Continue authorized work; do not repeat the same comment or create a duplicate issue. |
| A genuinely incompatible replacement is proposed | Use the existing migration-coordination path and hold accepted active behavior fixed. Compatible coexistence does not acquire a new approval gate. |

protected Cabinet route, ordinary Daychi schedule/preferences/reminders, accepted
API decisions, source-cutover conditions, account/reminder migration and deferred
gateway/consolidation work. No new watcher, ledger, retry service or forced sibling
harness installation is added.
