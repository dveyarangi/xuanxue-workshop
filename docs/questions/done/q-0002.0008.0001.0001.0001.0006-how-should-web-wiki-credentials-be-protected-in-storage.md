## Need and authority — 2026-10-12

The [accepted handoff](../../boundaries.md#accepted-web-wiki-sign-in-handoff) places
Cabinet credentials on Daychi, and the accepted lifetime/restoration direction
requires persistence across restarts. Cabinet can validate a presented random
credential from a hash; Daychi must recover that credential to present it.
The [security authority](../../agent-contract.md#security-authority) reserves this
security choice to Workshop. Neither native hash-only issuer storage nor accepted
web server custody selects protection for Daychi's recoverable values.

The customer is the wiki reader whose credential must remain confidential. The
observable case is disclosure of a copied session database or its backup: private
file permissions alone do not keep the copied values unreadable. The accepted choice below
addresses that disclosure, not complete compromise of the running service.
Under the proposed confidential web operations a copied user credential alone
still cannot authenticate a request without the application secret; database
disclosure must not be described as sufficient by itself for account takeover.

## Scoped source evidence — inspected 2026-10-12

Daychi `d2cde6b93ef79734e4de0438ddc2e138698214af` already has a private mounted
state directory, single worker/non-root service and volume-local SQLite backups in
[run.py](https://github.com/sleontenko/daychi/blob/d2cde6b93ef79734e4de0438ddc2e138698214af/deploy/daychee/run.py).
[admin.py](https://github.com/sleontenko/daychi/blob/d2cde6b93ef79734e4de0438ddc2e138698214af/practice_api/admin.py)
uses 0600 SQLite files, hashes opaque owner-session references and receives server
configuration at runtime. That establishes existing local storage/configuration
facilities, not encrypted wiki storage, deployment-key protection or reusable
owner authority. The pinned
[deployment dependencies](https://github.com/sleontenko/daychi/blob/d2cde6b93ef79734e4de0438ddc2e138698214af/deploy/daychee/requirements.txt)
contain FastAPI, Uvicorn and requests; no cryptographic storage library is declared
there. This proposal therefore has a dependency/key-management cost rather than
claiming all of the protection already exists.

[OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)
starts from the threat model, prefers established authenticated encryption and
separation of keys from data, and names the administrative cost of key management.
[The cryptography AESGCM documentation](https://cryptography.io/en/stable/hazmat/primitives/aead/#cryptography.hazmat.primitives.ciphers.aead.AESGCM)
provides a maintained implementation with nonce-uniqueness and authentication
requirements. These support feasibility and security conditions, not a blanket
claim that every backend must add field encryption. A full external key-management
service is not justified by this scoped case.

## Accepted answer — the user, 2026-10-12

The user replied "согласен" to the storage proposal. The complete accepted
guarantees live in
[credential storage protection](../../contracts/web-wiki-session.md#accepted-credential-storage-protection).
Cabinet uses existing hash-only random-credential checks;
Daychi hashes browser-cookie references and encrypts recoverable Cabinet tokens
and PKCE verifiers with AES-256-GCM, with a separate per-environment deployment
key, bound record context and failure/rotation/restore guarantees. It adds no
reader role or login method. A read-only copy of the credential database contains
no recoverable plaintext token material without that storage key.

The unselected simpler alternative was recoverable plaintext inside service-private storage,
with the confidential-client secret outside that database and the same file/log/
backup controls. It has fewer operational parts and no encryption dependency,
but database copies expose the credential values. Client authentication still
limits their direct use; it does not make the stored values confidential.

The accepted choice is authenticated encryption for this durable recoverable
store. Its cost is one maintained cryptographic dependency and a separate storage
key with recovery/rotation duties. It protects database-only disclosure and
record substitution, not a running-server compromise that yields both values
and keys. The decision provisions no key and authorizes no recipient
implementation. Actual storage/key protection and the remaining web protocol
retain their separate implementation, acceptance and proof requirements.
