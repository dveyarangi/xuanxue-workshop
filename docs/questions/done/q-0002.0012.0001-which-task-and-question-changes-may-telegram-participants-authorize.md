## Context and evidence

The user authorized reviewing and planning
[telegram-workshop-access](../../tickets/01-0020-telegram-workshop-access.md)
on 2026-10-12. The accepted [behavior](../../contracts/telegram-workshop.md#information-and-authority)
initially allowed informational answers and necessary conversation bookkeeping.
Its presentation section retains the Workshop workflow. The user has now amended
the authority boundary as recorded below.

The current entry requires question tracking. `questions.py` locates the store
relative to its own repository path, and even drawing a session window writes
session state. `.codex/hooks.json` invokes that machinery on entry and prompts.
Assignment review includes actions in original GitHub issues. A read-only execution
cannot simply run the unchanged workflow; a writable execution does not by itself
enforce a limited authority boundary. These facts prompted clarification of which
record changes group participants may authorize.

## Decision

The user, 2026-10-12: «бот может менять задачи и вопросы, если запросы разумны и
не конфликтуют с текущей архитектуре». Task/question changes within that condition
are authorized through the connected group. The proposed strictly informational
role and separate replacement for the Workshop question store are withdrawn.

The accepted authority is recorded in
[Information and authority](../../contracts/telegram-workshop.md#information-and-authority).
The operator still owns separately authorized code, architecture, agreement,
agent-rule, publication and cross-project assignment changes. Existing evidence
requirements apply to question closure and completion claims. Unclear requests
are clarified in the conversation; architecture conflicts do not authorize edits.

## Alternatives and next proof

The original task/question records can serve the accepted write scope; a second
authoritative question store is unnecessary. A fully writable checkout would still
grant more capability than the user authorized. File scope alone also cannot judge
whether a task amendment is reasonable or contradicts architecture.

With the role decision settled, the next proof covers instruction loading, source
reading, a permitted record change and denied out-of-scope mutations, as well as
semantic refusal of a conflicting task request. Recovery must distinguish applied
record changes from delivered replies. CLI help is not enforcement proof.
The draft [RFC](../../rfc/01-0020-telegram-workshop-access.md) retains that limitation.
