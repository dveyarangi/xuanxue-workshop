Opened at the user's request on 2026-10-04. Select a standard authentication
contract shared by Cabinet and Daychi, grounded in both projects' current
implementations and supported clients.

Accepted constraints live in [target contract](../boundaries.md#accepted-content-admission):
Cabinet owns accounts, credential issuance and admission; Cabinet web uses a
session cookie; native Daychi presents a Cabinet-issued bearer credential to both
backends. Daychi's call to Cabinet for content admission is bound to backend
consolidation. All admitted users receive the same content.

The decision must cover:

- Sign-in and credential acquisition for browser and native clients, including
  preservation of existing Cabinet access. Scope initial credential migration
  using the [dated migration context](q-0002.0007-how-will-daychi-migrate-schedule-users-and-reminders-to-cabinet-while-retaining-its-content-backend.md#initial-usage-and-ongoing-synchronization--2026-10-04).
- Token format and validation semantics, intended recipients and permitted uses.
- Expiry, renewal, logout and revocation, including recovery after temporary
  service failure and any agreed bound on revocation delay.
- The narrow service-to-service admission request and response, caller trust,
  error semantics and verification of interoperability.

Cabinet contributes provider and web-client constraints; Daychi contributes native
client and retained-content-backend constraints; Workshop records the shared
agreement, with the user deciding the standard. Cookie and bearer transport
alone do not select OAuth, OpenID Connect, JWT or an introspection protocol.
Opening this question did not authorize a standard or sibling implementation
change. The subsequent provisional acquisition agreement is recorded below.

## Native credential acquisition proposal — 2026-10-04

Cabinet source recheck at `62831447`: its typed auth routes support Telegram,
email link/code and Google sign-in. Successful controllers return `MeDto` and
set a Cabinet session cookie. `AuthService.issueSession` creates a token and
cookie; the current browser flows expose the cookie rather than a native bearer
acquisition contract. Google sign-in uses Cabinet as the client of Google's OAuth
flow, not as an authorization server for Daychi. Rolling cookie renewal already
exists; native credential renewal remains an adaptation to propose.

The next decision is the native application's credential-acquisition protocol.
Recommendation: OAuth 2.0 authorization code with PKCE, using Cabinet-owned sign-in
and issuing a Cabinet bearer credential to Daychi. This reuses Cabinet's sign-in
methods behind one native handoff but requires new authorization/code-exchange
support. Alternative: native calls to Cabinet sign-in APIs, beginning with its
email-code flow; initially smaller for that method, but native support for other
methods and credential exchange needs additional contracts. Neither alternative
changes the accepted account/admission owner.

Primary references: [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html) for
native OAuth authorization through an external user-agent and PKCE;
[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) for current OAuth security
practice. This proposal was presented for agreement; its disposition follows.

## Provisional agreement — 2026-10-04

authorization-code-and-PKCE handoff, explicitly as a straw dog pending the
[gateway question](q-0002.0010-should-clients-reach-cabinet-and-daychi-through-a-shared-gateway.md)

dog live in [native credential acquisition](../boundaries.md#accepted-native-credential-acquisition).
This is an accepted provisional default, not a final authentication standard.
No sibling implementation assignment was issued by this agreement.

The gateway is [deferred by the user, 2026-10-05](../boundaries.md#accepted-gateway-deferral).
Standardization proceeds against the accepted direct connections, without waiting
for a gateway initiative. Native acquisition was provisional at that decision;
the method was reaffirmed on 2026-10-08. Exact native wire, token representation,
narrow admission schema, caller trust and interoperability remain unresolved.
The subsequent native lifecycle and local sign-out decisions are recorded below.

## Sign-out scope accepted — 2026-10-05

The user accepted the simple, installation-scoped behavior: explicit sign-out
ends authenticated use in the current client installation, leaving other
Cabinet and Daychi clients signed in. This does not select server-side credential
revocation mechanics. The accepted discard of local unsynced reminder and
lead-time edits remains in force, while Cabinet's already-accepted state remains.
The decision lives in [sign-out scope](../boundaries.md#accepted-sign-out-scope).
Expiry, renewal, other revocation behavior and the executable contracts remain
open in this question at that decision. Native lifetime/renewal was subsequently
accepted below; remaining revocation mechanics and executable contracts remain open.

## Acquisition reaffirmation and local sign-out accepted — 2026-10-08

The user reaffirmed the existing browser/code-and-PKCE method and corrected a
repeated method-approval request. The user also accepted immediate local sign-out
without waiting for remote revocation, no retained retry credential and explicit
incomplete exit on local deletion failure. Their authoritative homes are
[native acquisition](../contracts/native-account-session.md#accepted-native-credential-acquisition)
and [local sign-out policy](../contracts/native-account-session.md#accepted-local-sign-out-and-failure-policy).
The user subsequently accepted
[account-block recovery](../contracts/native-account-session.md#accepted-account-block-recovery):
retain the credential without account use while blocked, then recover after a
successful authoritative check if the credential remains valid. Exact wire and
server revocation mechanics remain proposed.

The user subsequently accepted the
[registered native callback](../contracts/native-account-session.md#accepted-registered-callback)
`su.xuanxue.daychi:/oauth/cabinet` with existing invitation compatibility and

On 2026-10-09 the user accepted
