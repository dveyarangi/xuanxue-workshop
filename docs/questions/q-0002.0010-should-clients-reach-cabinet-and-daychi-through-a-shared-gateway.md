This question holds whether a shared gateway is needed between the clients and
the project backends, what responsibility it would hold, and whether its
disposition changes native credential acquisition. Establish the concrete need
and compare existing direct connections before proposing another service.
Cabinet's accepted account and admission authority is held fixed; this question
does not authorize a separate identity owner, backend consolidation or a gateway
implementation.

The [provisional native acquisition contract](../boundaries.md#provisional-native-credential-acquisition)
is the current default. After the harness update to v25, the straw dog's
`question` attribute names this question. If the question becomes work, assign it
to the owning ticket; the binding continues to name the question. Its answer
must record the gateway disposition and resulting acquisition contract, whether
that retains the current handoff or replaces it.

Provider: Cabinet for sign-in, issuance and authoritative admission. Consumers:
Daychi native clients and its retained content backend; Cabinet web compatibility
must be preserved. Cabinet and Daychi retain their own implementation and release
ownership. Workshop records the shared agreement; the user decides the gateway
disposition. Responsible gateway contributors require agreement if work is
selected.

## Resumed alignment — 2026-10-05

Accepted by the user, 2026-10-05: keep a shared gateway deferred until the project
contributions demonstrate a concrete client or deployment requirement that the
accepted direct connections cannot satisfy. Cabinet remains the account and
admission authority; Daychi retains its content backend. The native browser
handoff remains provisional. Deferring a gateway does not make that acquisition
contract final or implement the cross-project connections.

Existing target: Daychi calls Cabinet for schedule and account/reminder state,
and its retained backend for content. Adding a shared front door would require
agreed routing, ownership, operation and failure behavior. The source inventory
has not established a deployed integration or a requirement for that extra
component. Compare that additional work with leaving clients responsible for
reaching the two providers, using project-agent evidence before selecting work.

The decision is recorded in
[accepted gateway deferral](../boundaries.md#accepted-gateway-deferral).
Credential standardization can proceed against the accepted direct connections;
it does not need to wait for a gateway initiative. The native handoff remains a
straw dog bound to this deferred question, which does not make it due.
