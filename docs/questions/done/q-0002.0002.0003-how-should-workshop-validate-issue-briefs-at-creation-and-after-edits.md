## Current loop audit — 2026-10-06

The user requested an instruction/process/principle/invariant audit before
improving issue creation, after Daychi issue 6 accumulated host-typo investigation
history and conversational evolution. This is mechanism work. No instruction
amendment has been agreed or implemented by this audit.

The inspected chain has two record shapes: local coordination tickets are owned
by the ticket mechanism; issued cross-project assignments use the collaboration
companion format. Reconciliation owns collection, comparison, disposition,
preparation and publication, and the installed local L13 binds its remaining
outcomes to ticket/impact/breakdown approval. Local L14 and the review skill own
the issue evidence/acceptance return loop. The recipient collaboration skill
owns discovery and reporting under each project operator.

Existing explicit guarantees: source investigation precedes evidence requests;
remaining actions derive from a current comparison; existing assignments are
reused; RC2 blocks incomplete shared contract shapes even for Planned publication;
paired implementations use one immutable authority and common cases; owners,
stage-specific prerequisites, observable evidence and acceptance responsibilities
are explicit; publication is read back; implementation and deployment remain
distinct from contract and acceptance; original-issue timelines and linked
artifacts support review, records and acceptance.

The local ticket format states that shaped tickets hold actual work and that
resolved decisions land elsewhere. Its stage depends on an RFC Plan bullet;
incepted tickets may contain arbitrary sections. P7 and P11 reach alignment,
where resolutions rewrite tickets and a final consistency sweep occurs. The
external issue format enumerates content and dependency fields, but has no
explicit creation/edit-time editorial gate for a standalone current brief.
Reconciliation requires coherent records and counterexample review of the issue
set; it does not explicitly require a separate recipient-perspective/editorial
pass or put all issue edits through that gate. No independent pre-publication
grader is required by the active instruction. Mechanism declarations name
operator grading as evidence of the mechanism working; that is a separate
occasion, not every issue publication.

Mechanical checks hold instruction installation, declarations, local record
shape, links and example assertions. tickets.py reads local ticket files only,
not remote issue bodies, and explicitly checks format rather than semantics.
The local check-contract-review.py validates this pilot's literal examples and
links; it is not a reusable issue-content validator. Readback proves equality
with the prepared body, not that the prepared body was a good brief.

The improvement question concerns where the brief-quality invariant and its
publication/edit-time check should live, what can be mechanically checked, and
how semantic output is reviewed. Existing shared contracts, ownership,
execution gates and approval checkpoints remain fixed.

Clarity means the recipient can recover the current outcome, scope, required
action, governing authority, dependencies, freedom and proof without conversation
history or Workshop layout knowledge; links resolve in its actual context and
the body excludes obsolete instructions and irrelevant investigation history.
Consistency means meanings agree with governing requirements, related assignments
and their common cases, with viable dependency/transition states and no invented
obligations. Completeness means every in-scope obligation has an owner/action and
acceptance proof, or evidence that it is already fulfilled; all applicable
contract dimensions and cross-project integration work are accounted for, with
explicit exclusions, deferrals and genuine unknowns.

The user challenged issue ownership because the requirements apply throughout
the loop. The revised recommendation gives coordinate ownership of the shared
validation set, including its detailed criteria. The earlier direct-invocation
argument does not establish ownership: installed rules also reach an independently
invoked stage skill. This replaces the issue-owned-block proposal.

The shared criteria cover information preserved from observations through agreed
obligations, decomposition, recipient instructions and accepted evidence. Clarity
is assessed for each output's next reader; consistency includes provenance and
agreement across transformations; completeness is relative to the declared scope
and stage. An observation can be complete with explicitly bounded unknowns. An
implementation assignment cannot leave a shared contract choice unresolved.
Overall completion requires accepted evidence and reconciled records for its
declared outcome, not merely complete issue text.

Stage skills own how they produce and check their particular outputs. Shared

by changing rule ownership. This remains a proposed ownership design, not an
installed mechanism change.

Execution is one continuous pass where possible: retain existing analysis, draft
and repair in place, use one review result, and repeat only checks invalidated by
changes. A factual edit does not force a new RFC, ticket, contract review or
subagent. Substantive shared work still receives the agreed recipient and set
review. Mechanical checks cover structure, references and executable examples;
semantic interpretation remains an explicit review with bounded conclusions.
The existing human decision/publication checkpoints are not duplicated per stage.

Vertical slicing means a small independently demonstrable coordination outcome,
possibly spanning multiple projects. A published handoff and a working integration
remain different completion claims. Outstanding execution/integration retains its
owner when a publication outcome completes.

## Independent discovery material — 2026-10-06

The user proposed separating observation, reconciliation and issuing, with ticket

functional description of independently owned projects, shared agreements,
revision-specific evidence, recipient assignments and acceptance. It received no

### Families

These are structural comparisons, not claims that the activity belongs to any one established discipline. The ladders describe increasing capability; they are not published maturity models.

**1. Conformance assessment and assurance**

**Confident analogy:** A claim about a project is evaluated against a criterion using evidence. The important unit is therefore not “project status” but *claim, applicable agreement, revision, evidence, and evaluation*. A coordinator can distinguish a failed requirement from insufficient evidence and from a requirement that does not apply.

Possible ladder: self-reported compliance → reproducible checks → explicit coverage of requirements → independent assessment → continued validity checks as implementations and agreements change.

Characteristic failure modes: evidence demonstrates a convenient proxy rather than the actual obligation; “passed” survives after its supporting revision changes; exceptions silently become the effective standard; the evaluator mistakes absent evidence for failure or compliance.

**Hypothesis to test:** The coordinator needs an assurance argument for significant claims. That depends on consequence and uncertainty: many ordinary requirements need only a directly reproducible check.

This family explains evaluation well. It does not itself explain who may change the agreement or authorize implementation.

**2. Distributed protocols and replicated knowledge**

**Confident analogy:** Participants act on different, delayed views of a changing world. An assignment crosses a boundary without carrying the sender’s working memory. Acknowledgement, implementation, and acceptance are different events.

Possible ladder: informal messages → identifiable requests and replies → explicit revision and dependency references → handling of duplicates, supersession, and stale responses → deliberate recovery from interrupted coordination.

Characteristic failure modes: a recipient implements an obsolete assignment; delivery is mistaken for agreement; two individually reasonable actions conflict because they assume different starting states; retries cause duplicate work; an old completion report overwrites a newer understanding.

**Hypothesis to test:** Some coordinated changes require protocol-like staging. A provider/consumer migration may need compatibility windows and ordered transitions. Independent adoption of a documentation standard may need no coordinated transition at all.

The analogy weakens when it treats people as deterministic nodes. Participants can reinterpret, negotiate, and refuse; those are meaningful outcomes, not transport failures.

**3. Systems integration and configuration management**

**Confident analogy:** Correct components do not guarantee a correct composition. The object being evaluated may be a *particular combination* of provider version, consumer version, configuration, and shared agreement.

Possible ladder: inventory of component behavior → explicit interface expectations → checks across relevant combinations → planned transition paths → continued detection of incompatible combinations.

Characteristic failure modes: both sides pass different interpretations of the same contract; only the intended final combination is tested while the deployed transition is impossible; ownership falls into the gap between components; interface records omit configuration that changes behavior.

**Hypothesis to test:** The coordination activity needs a persistent notion of an integration baseline. This becomes compelling if reproducing an observed incompatibility requires several revisions together. It is less compelling for standards applied independently to each repository.

This family exposes two different shapes inside the task: *compatibility of interacting participants* and *conformance of separate participants*. They can share administrative machinery without sharing the same correctness condition.

**4. Compilation, linking, and artifact production**

**Confident analogy:** A shared agreement is transformed into recipient-specific work. Some meaning must survive every transformation. An assignment can be locally clear yet fail to preserve the agreement; several assignments can each look sound yet fail when combined.

Possible ladder: hand-written instructions → explicit inputs and required outputs → checks for unresolved terms and missing dependencies → checks across assignments → traceable regeneration when source agreements change.

Characteristic failure modes: decomposition drops a requirement; assumptions become accidental requirements; copied instructions drift; a recipient receives references it cannot resolve; generated detail appears authoritative despite lacking an approved source.

**Hypothesis to test:** Assignment preparation could benefit from “type checking”: checking ownership, prerequisites, expected evidence, and dependencies before publication. This need not imply a rigid schema or automated generator.

The limit is substantial: normative prose is not necessarily executable, and interpretation may produce a new decision. Calling every transformation compilation can hide where judgment enters.

**5. Commissioned work and delegated authority**

**Confident analogy:** One party requests an outcome from another party that controls its own means of delivery. A useful assignment therefore establishes obligations, decision rights, dependencies, and what counts as completion.

Possible ladder: request an activity → specify an observable outcome → agree responsibilities and acceptance criteria → manage changes and exceptions explicitly → evaluate delivery while retaining responsibility for the original objective.

Characteristic failure modes: the coordinator assumes authority it does not hold; implementation effort is accepted in place of the requested result; acceptance criteria change after delivery; an assignment depends on another owner’s unconfirmed cooperation; “approved” conceals disagreement about who approved what.

**Hypothesis to test:** Acceptance may need several parties. A provider can establish that it delivered an interface; a consumer may establish that the interface satisfies its need; a contract owner may establish conformance. One acceptance event is sufficient only if its scope and authority cover the necessary judgment.

This family foregrounds accountability. It can overformalize ordinary collaboration if every clarification becomes a contractual amendment.

### What the tasking smuggled in

- **A single coordinator can establish the relevant truth.** It may instead assemble claims whose authority remains with project owners. Observed behavior, intended behavior, and authorized requirements have different sources.
- **Shared agreements are sufficiently definite to compare against.** A discrepancy might expose an implementation defect, an ambiguous agreement, incompatible local requirements, or a mistaken observation. These imply different work.
- **Revision-specific evidence remains representative.** Configuration, dependencies, deployed versions, and operating conditions may matter as much as a repository revision.
- **Approval precedes decomposition cleanly.** Decomposition can expose missing decisions. Conversely, approving a broad objective does not necessarily approve every implementation choice that a decomposition introduces.
- **Clear assignments are mutually consistent.** Clarity is local; consistency concerns relationships. Neither establishes completeness: all assignments can agree while collectively omitting an obligation.
- **Publication creates an obligation.** That depends on authority and the receiving project’s commitments. Publication, receipt, acknowledgement, and commitment need not coincide.
- **Current records describe one current state.** Intended, implemented, deployed, observed, and accepted states may legitimately differ.

**Separate meanings do not automatically require separate persistent records.** Observation, decision, decomposition, publication, and acceptance warrant distinguishable provenance. Whether each needs its own record is a further question.

Separation gains value when an item has an independent lifecycle, owner, reuse pattern, or historical significance. One observation might support several decisions; one decision might generate many assignments; publication may occur repeatedly; acceptance may be scoped or revoked.

Conversely, five record types can manufacture synchronization work where one small work item with an event history would preserve everything needed. The useful tests are:

- Can one item change without changing the others?
- Must an earlier state remain independently referable?
- Can different people legitimately disagree about its status?
- Does it have multiple consumers or a different retention requirement?

These tests support either consolidation or separation depending on the actual cases. They do not establish a universal record architecture.

### Nothing to take

Do not import distributed consensus merely because several projects participate, a compiler merely because assignments are derived, formal certification merely because evidence is checked, or procurement bureaucracy merely because work is delegated.

None of these analogies establishes the need for a central database, a canonical intermediate representation, a fixed number of stages, or autonomous acceptance. Those remain hypotheses requiring concrete cases—especially cases where interacting interfaces and independently applied standards force different structures.

## Proposed separation: impact assessment — 2026-10-06

This records discussion, not approval to amend mechanisms or publish assignments.
The customer is the recipient agent and operator, who need a current executable
brief without Workshop conversation history. The observed failures are shared
contract ambiguity, missed evidence in issue mentions, investigation requested
despite accessible source, and investigation history left in a live brief. The
existing rules address several of these but have no universal issue-edit gate.
PRODUCT.md also explicitly includes shared operational standards; this supplies
a second application alongside interacting provider/consumer assignments.



### Impact

- Separate observation from shared judgment and assignment production. A per-repo
  observer supplies source revision, inspection scope, owners, interfaces and
  observable guarantees, source/tests supporting each finding, independently
  checked deployment/configuration, relevant standards/adoption, changes against
  its previous observation, and explicit unknowns. Repository changes can trigger
  inspection but do not themselves prove a changed guarantee. Scripts can gather
  revisions and validate record structure; source interpretation remains review.
- Existing current-system.md and reconcile collection rules define useful subject
  matter but no uniform per-project extraction record or completeness/freshness
  contract. Define that output before delegating routine extraction. Reuse its
  evidence across findings and avoid reproducing entire project architectures.
- Reconciliation consumes observations and governing agreements, retaining all
  existing dispositions: no action, factual correction, implementation correction
  under an unchanged contract, missing evidence, unresolved shared decision,
  accepted migration, or deferred work. Contract amendments require the decision
  owner; observed code cannot silently redefine accepted obligations.
- Issuing consumes approved outcomes and remaining recipient actions against
  authoritative requirements. Inputs include adoption of standards and correction
  under unchanged contracts, not only contract-document deltas. Evidence/design
  requests remain distinct from implementation assignments. Decomposition or
  drafting that exposes a missing shared decision returns to alignment.
- Ticketing evaluates independently verifiable outcomes, dependencies, effort and
  risk. Preserve the current distinction between a coordinating outcome and its
  several addressed issues. Use child tickets where preparation has an independent
  lifecycle; do not require a duplicate local implementation ticket per recipient.
  Even an inline pass retains its stage/resumption point in its existing report.
- The issue cycle is scoped planning of outcome/requirements/coverage, draft
  production, recipient-perspective and issue-set verification, whole-body
  maintenance, authorized publication and readback. The same relevant gates apply
  to edits of existing issues. A fresh recipient review uses only the proposed
  brief, reachable cited authorities and the recipient repository/instructions;
  it reconstructs the work, dependencies, shared meanings and acceptance evidence
  without author explanations. A separate set-level check covers completeness,
  consistency and viable transition states across recipients.
- A current issue states current work and necessary context. Decisions and
  investigation history retain their proper record homes; a useful historical
  rationale may be linked without making the reader reconstruct the assignment.
  Any maintenance edit that changes a requirement or dependency invalidates the
  corresponding earlier review. Readback compares both intended content and links.
- Completion evidence still returns through assignment review, including timeline
  mentions and referenced PRs/commits. Reconcile affected records before acceptance
  and closure, and reassess direct dependents. Implementation, deployment and joint
  integration are separate claims with separately scoped evidence.

### Hidden edges

- A pair can be mutually consistent while omitting an agreed guarantee. Trace every
  in-scope obligation to an owner action and acceptance check, or explicitly explain
  why existing behavior already satisfies it. Check shared contract cases as a set.
- Provider/consumer compatibility and independent adoption of a common standard
  have different acceptance conditions. Do not impose a joint rollout where none
  is needed, or accept two independently passing checks as integration proof.
- An inaccessible reference is unusable authority for that recipient. Exercise
  pinned links and required companion assets from the installed/recipient context;
  Workshop-local path validity is insufficient.
- Changes after collection or during drafting require scoped evidence refresh.
  Preserve revision identity for decisions, source inspection, published briefs
  and acceptance evidence; stale completion cannot satisfy a changed assignment.
- Compatibility must hold during migration as well as at its endpoint. Assign
  transition and integration proof to owners, including work that falls between
  individual project issues. Superseded assignments need explicit disposition.
- Full automation cannot prove semantic compatibility from prose. Structural
  checks and independent readings are bounded evidence; failures route back to
  the responsible stage instead of inventing missing requirements.

### Leave alone

- Accepted application contracts, provider/consumer/data ownership and each
  project's freedom over internal design.
- The complete 13-dimension contract-shape coverage, explicit applicability,
  immutable shared authority and common cases; incomplete implementation briefs
  remain blocked even when marked Planned.
- Existing recipient discovery/reporting, original-issue continuity, timeline and
  artifact inspection, direct dependency semantics, publication/execution/
  acceptance distinctions, and current operator checkpoints.
- Current assignment state and existing local work. This assessment neither
  republishes issues nor adopts a monitoring product or architecture change.

### Recommendation

Proceed with alignment on the separation, while narrowing record proliferation.
Retain outcome-based ticketing rather than automatically pairing every issue with
a local ticket. Before implementing the refactor, map every existing rule to its
owner, invocation occasion and verification; explicitly decide any removed rule.
Exercise both a provider/consumer change and an independently adopted standard.
Use counterexamples that must fail: contradictory contract interpretations,
collectively omitted guarantees, inaccessible authorities, stale evidence,
investigation history in a current brief, and an edit invalidating prior review.
No new skill, declaration, record format or enforcement has been installed.
