# Prepare and maintain addressed work

Read the approved outcome, governing requirements, affected ownership, current
evidence and existing assignments. Confirm the remaining gap; continue an issue
covering the same action. Use the configured exchange format and tracker.
Design and evidence requests identify their unresolved question and cannot
stand in for a settled implementation contract.

## Derive and draft

Derive recipient actions together from one immutable contract, ownership,
observed state and approved change. For every shared obligation identify the
provider action, consumer action and common expected outcome, or evidence that
an obligation is already fulfilled. Independent standard adoption uses its
applicable obligations without inventing provider/consumer dependencies.
Use the draft itself for this reasoning; no mapping register is required.

Each brief supplies the recipient's goal, required action, necessary current
context, scope and exclusions, shared authority, direct dependencies and acceptance
evidence. State which activity each dependency blocks and who accepts its proof.
Retain project freedom over internal design. Shared meanings are never selected
independently in recipient prose.

Prepare complete boundary summaries when supplying instructions. Compare with
the confirmed installed baseline; absence of a baseline means unverified adoption,
not a regression. Keep tasks, rationale and evidence outside the summary.

## Validate and maintain

Apply the installed shared validation set while drafting and before publication.
Read each substantive implementation brief from the recipient's position, using
only that brief, accessible cited authorities and its own repository/instructions.
Reconstruct the intended implementation obligations, dependencies, internal freedom
and evidence. Use a fresh independent reader for new or materially changed shared
implementation obligations. Resolve differences without private explanatory context.

Review the set for compatibility and coverage: individually clear briefs can
collectively omit an obligation. Probe applicable boundary, empty, invalid,
failure, update and transition cases against the common contract examples.
An allowed pair of incompatible implementations blocks publication.

Maintain the entire body as a current assignment. Remove superseded instructions
and irrelevant investigation history; link durable rationale where useful.
Do not compress away context necessary for independent implementation.
A semantic edit invalidates the affected review; a factual/editorial edit needs
coherence and reference checks, not a new ticket, RFC or independent agent.

## Publish and read back

Observe the existing publication authority. Re-read current issue content and
check relevant contract, source and dependency changes since draft review.
Reconcile intervening contributions and revalidate affected findings before writing.

Read back each published body, recipient label, immutable authority and direct
dependency link against the validated draft. If only part of a set publishes,
retain successful issue identities and the remaining action in the existing pass;
resume without duplicates or automatic closure. Report partial publication honestly.
Every published implementation brief independently passes the contract gate.

Eligibility follows explicit dependencies and recipient operator authority.
Publication is not implementation, deployment or acceptance. Do not create an
extra Ready approval. Preserve pending recipient and integration work when the
coordinating handoff finishes.

<installed by="coordinate">
**RC1** For cross-project work, state shared boundary guarantees and observable acceptance
outcomes. Projects own executable definitions and internal mechanisms; the shared
contract fixes their externally observable shape. Inspect implementation details to verify guarantees; bring them to
alignment when they reveal an unresolved shared obligation or require changing
accepted ownership, behavior, compatibility or scope.

**RC2** Cross-project implementation assignments prescribe one fully specified contract
through an accessible immutable authority and common conformance cases. Apply
.agents/skills/coordinate/CONTRACT-SHAPE.md to every applicable dimension, with a
reason for inapplicability. Leave no recipient choice that can change shared
formats, parameters, meanings, guarantees or interoperability. Internal designs
may differ. Each recipient's brief and cited authority must suffice without
Workshop session context; compatible implementations must follow from the briefs.
An incomplete shared shape blocks implementation publication, including Planned
issues. Design/evidence requests cannot substitute for this gate.

**CQ1** For cross-project work, apply .agents/skills/coordinate/VALIDATION.md during
inception and validation. Establish clarity for the next reader, consistency
with governing agreements and related work, and completeness of scoped obligations.
Derive recipient tasks from the same contract and ownership; assess individual
understanding and set-wide coverage. Revalidate affected meanings after edits.
Reduce process steps, never context required for compatible implementations.
Reuse valid evidence; stage changes add no approval.
</installed>
