The user accepted [content-admission placement](../boundaries.md#accepted-content-admission)
on 2026-10-04. This question holds the remaining credential and executable-check contract:
native-client acquisition, renewal, narrow check inputs and
outputs and verification. Initial credential-migration scope uses the
[dated migration context](q-0002.0007-how-will-daychi-migrate-schedule-users-and-reminders-to-cabinet-while-retaining-its-content-backend.md#initial-usage-and-ongoing-synchronization--2026-10-04). All admitted users
receive the same content. The accepted temporary-failure behavior preserves stored client
sessions; access refusal and service unavailability must remain distinguishable.

On 2026-10-04 the user accepted Cabinet web session cookies and Cabinet-issued bearer
credentials for native Daychi, presented to both backends through `Authorization: Bearer ...`.
Cabinet owns issuance and authoritative validation; Daychi passes the credential to the
accepted admission check. This settles transport and authority, not the authentication
protocol or credential lifecycle. The user requested a separate
[standardization question](q-0002.0008.0001.0001-which-authentication-standard-should-cabinet-and-daychi-adopt.md).

On 2026-10-04 the user accepted the
[Cabinet-owned browser/code-and-PKCE handoff](../boundaries.md#accepted-native-credential-acquisition)
as a straw dog pending the
[gateway question](q-0002.0010-should-clients-reach-cabinet-and-daychi-through-a-shared-gateway.md).
At that decision acquisition was provisionally selected. The method was reaffirmed
on 2026-10-08. The complete native wire and server revocation mechanics were accepted
on 2026-10-09; the separate content-admission check remains open. Accepted native
acquisition, lifecycle and local sign-out/failure policy live in the
[native-session contract](../contracts/native-account-session.md).

Current source evidence: Cabinet accepts a session cookie through
[AuthGuard](https://github.com/gregoryKot/xuanxue-cabinet/blob/27f3e7bf50ac0a1e1f981519b7009fc2a19e7042/api/src/auth/auth.guard.ts); Daychi clients use bearer
credentials in [their access client](https://github.com/sleontenko/daychi/blob/5f9ba442e04cd5dfa70527b9e670b491c491888c/apps/practice-app/src/features/access/session.ts).
The existing Cabinet [GET /auth/me](https://github.com/gregoryKot/xuanxue-cabinet/blob/27f3e7bf50ac0a1e1f981519b7009fc2a19e7042/api/src/auth/auth.controller.ts)
returns a profile and is not the agreed narrow admission-check contract. Contributions should
reuse Cabinet's authoritative validation rather than duplicate its user/session rules.
