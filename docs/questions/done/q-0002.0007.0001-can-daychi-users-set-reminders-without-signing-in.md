The accepted [schedule access](../../boundaries.md#accepted-schedule-access)
allows browsing without authentication. Accepted
[reminder selections](../../boundaries.md#accepted-reminder-selections) are shared
through Cabinet for authenticated users; [Daychi delivery](../../boundaries.md#accepted-daychi-reminder-delivery)
is local, based on refreshed server data. These decisions do not settle reminders
before sign-in.

User scenario: a person installs Daychi, discovers a lesson they want to try,
and asks to be reminded before it starts. Must that person first obtain and
sign into a Cabinet account?

Assistant recommendation, unaccepted: allow local reminder selections without
sign-in; account sharing becomes available after sign-in. This avoids adding
an account step to trying a publicly listed lesson. It introduces local guest
state and requires a proposal for associating or reconciling it with an existing
account selection. Requiring sign-in keeps one authoritative preference store
but adds friction before the first reminder. No guest identity or merge rule
is accepted by opening this question.

Source finding, 2026-10-04: reminders without sign-in are already available.
The [app layout](https://github.com/sleontenko/daychi/blob/5f9ba442e04cd5dfa70527b9e670b491c491888c/apps/practice-app/src/app/_layout.tsx) opens
the schedule without an authentication gate; the
[schedule controls](https://github.com/sleontenko/daychi/blob/5f9ba442e04cd5dfa70527b9e670b491c491888c/apps/practice-app/src/features/schedule/schedule-screen.tsx)
call selection and reminder settings without requiring access. The
[schedule hook](https://github.com/sleontenko/daychi/blob/5f9ba442e04cd5dfa70527b9e670b491c491888c/apps/practice-app/src/features/schedule/use-schedule.ts)
stores choices locally and requests OS notification permission, not account login.
