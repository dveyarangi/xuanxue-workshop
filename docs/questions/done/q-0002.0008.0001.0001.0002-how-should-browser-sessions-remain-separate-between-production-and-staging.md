## Evidence and unresolved consequence

The user asked on 2026-10-13 how production would avoid colliding with
`staging.xuanxue.su`. The accepted [web-wiki contract](../../contracts/web-wiki-session.md#accepted-shared-browser-session)
uses `session; Domain=xuanxue.su; Path=/` for production. This necessarily
includes staging in browser delivery; cookie attributes cannot exclude one
matching subdomain. [MDN, Domain](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#domain)
documents this behavior. Existing Cabinet source at
[67d5cbd, session-cookie.ts](https://github.com/gregoryKot/xuanxue-cabinet/blob/67d5cbd0041daa13c6973b657479e45a6716486f/api/src/auth/session-cookie.ts)
uses a host-only cookie with the same `session` name and a first-match parser.
After production domain sharing, a browser with both cookies could present two
same-name values at staging. Distinct hosts alone no longer isolate the sessions.

The Cabinet–wiki production shared-login decision remains fixed. Environment
isolation is its unresolved consequence, not a proposal for another login system.

## Accepted answer — 2026-10-13

The user replied "ok" to the staging mapping and separate-cookie proposal.
The operative answer is the [accepted environment profiles](../../contracts/web-wiki-session.md#accepted-production-and-staging-separation).
The following argument retains the agreed scope and its limitation; recipient
implementation and actual DNS/HTTPS/runtime proof remain work.

Proposed public origins are Cabinet `https://xuanxue.su` and wiki
`https://wiki.xuanxue.su` in production; Cabinet
`https://staging.xuanxue.su` and wiki `https://wiki.staging.xuanxue.su` in
staging. The staging wiki hostname routes to Daychi's staging deployment;
production wiki routes to its production deployment. This is proposed mapping,
not evidence that DNS, HTTPS or either wiki deployment has been provisioned.

Use `session_staging; Domain=staging.xuanxue.su; Path=/; Secure; HttpOnly;
SameSite=Lax` for staging, while production retains its accepted cookie.
Staging reads only its own cookie and never issues, renews or expires the
production cookie. Production and staging use distinct signing keys and account
stores, with each wiki checker fixed to its matching Cabinet environment.
Migration clears staging's old host-only `session` without clearing the
production domain cookie. Deployment selection is explicit: `NODE_ENV=production`
alone cannot distinguish a production build deployed to staging.

The staging wiki receives `session_staging` and forwards only that cookie to
`https://staging.xuanxue.su/api/auth/session`; production wiki forwards only
`session` to `https://xuanxue.su/api/auth/session`. Staging sign-in entry and
logout use staging Cabinet's `/wiki` and `/logout`, and staging `/wiki`
returns only to the fixed staging wiki origin with the accepted relative
`returnTo` validation. Environment origins, cookie names and cookie domains are
fixed deployment configuration, not selected by browser parameters or inferred
from `NODE_ENV`. The two-site staging flow requires the corresponding scoped
Cabinet and Daychi changes, not a DNS alias of production wiki.

This prevents normal login, renewal and logout collisions; it does not prevent
production credentials from reaching the staging server. If that stronger
separation is required, staging needs a domain outside `xuanxue.su` or the
accepted production cookie scope must change. No domain move is selected here.

Acceptance would exercise production and staging sign-in, renewal and logout in
the same browser in both orders, prove credentials are not accepted across
environments, and include migration from an existing staging host-only cookie.
This is an accepted amendment, not deployed capability. Both existing recipient
assignments were updated and read back against amended immutable authority
`25def59e25fc847764cc43de8d963bf62a16512e`: [Cabinet 12](https://github.com/dveyarangi/xuanxue-workshop/issues/12)
and [Daychi 13](https://github.com/dveyarangi/xuanxue-workshop/issues/13).
