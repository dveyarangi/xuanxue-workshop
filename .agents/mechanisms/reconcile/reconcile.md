# reconcile — evidence-backed boundary records and actionable project updates

- **instruction** `.agents/skills/reconcile/SKILL.md`
- **state** installed

## How it works

The /reconcile skill compares independent projects with their coordinating records.
Its procedure is portable; the project's local rules supply source pointers and
bind the pass to maintenance. The pass has collection, comparison, resolution, publication preparation and
publication stages. Decision and delivery cycles return their results to the same
pass; its report holds the stage and resumption point. Completed collection remains
evidence unless affected sources change. Addressed work derives from the remaining
comparison delta, not from an old proposal. The ticket mechanism shapes local
coordination outcomes; published project issues can be their verified outputs.
A handoff's completion does not establish recipient implementation or integration.
It owns no application
contracts, project routing convention or issue format.

Its boundary-scope rule is read during reconciliation and alignment. Shared
guarantees need coordinated acceptance; internal project designs need evidence
against those guarantees. The rule separates these occasions without transferring
executable-interface or implementation ownership.

Its primary issue-output invariant is one fully prescribed shared boundary shape
for coordinated implementation assignments. A project can author executable
definitions in its own repository without defining a different interface for its
counterpart. The contract-shape reference separates externally observable
dimensions from internal choices. Missing shared meanings prevent implementation
publication, including Planned work; a request for design input is a different
outcome. A common immutable authority and shared conformance cases make recipient
instructions assessable as one coherent result.

## What it produces, and who reads it

The maintenance report gives the operator the pass stage, resumption point,
evidence and dispositions per boundary.
Updated factual records and derived summaries are read by coordinating and project
agents. Local tickets use the ticket mechanism's existing record shape and hold
coordination outcomes. Addressed issues produced by those tickets are read by the
responsible project agent and its operator.
The installed scope and shared-contract rules are read by reconciliation and alignment agents.
The contract-shape reference is read when comparing or resolving a boundary and
when assessing proposed implementation assignments.
These use the existing project records and issue format supplied through context;
this mechanism creates no independent record kind or register.

## Not yet at the shape

No independent validator can prove semantic compatibility from prose. Source checks,
project evidence and explicit uncertainty bound the conclusions of each pass.

## What retires this

Retire it when cross-project boundary reconciliation ceases to be a responsibility
of the coordinating project or another accepted mechanism assumes the whole pass.

## What would show it working, graded by someone who did not build it

The operator reviews a preview containing an unchanged boundary, documentation drift,
a project-action deviation, an unimplemented target and missing evidence. It must
preserve accepted promises, avoid duplicate issues, emit an unambiguous summary and
avoid claiming implementation or deployment without evidence. The shared checkers
must reject a missing instruction file or a drifted installed invocation block.
The operator also checks that a boundary proposal states shared guarantees and
leaves project design to its owners. A proposed internal design reaches alignment
only when it reveals an unresolved cross-project obligation or changes an accepted
boundary. Both installed scope blocks must match their owning rule. A preview containing new
assignments must show the ticket mechanism's impact and approval step before local
tickets are minted. One coordinated outcome may produce several project issues;
it must not become a duplicate local copy of recipient implementation work. A
handoff ticket completes against verified publication criteria, while an integration
ticket remains incomplete without integration evidence. Routine factual corrections
and continuing an assignment within its scope require no extra ticket.
The installed ticket block must match its owning rule.

For the shared-contract invariant, the operator grades a pair whose scopes sound
compatible but permit different parameters, time boundaries, formats or refresh
semantics: publication must be blocked. A pair referencing the same complete,
immutable contract and common conformance cases can pass despite different
internal structures. A design/evidence request cannot be counted as that compatible
implementation pair. Both installed RC2 blocks must match their authored rule;
binding checks alone cannot establish semantic completeness of an issue set.

The operator also evaluates a resumed pass after alignment: collection is retained,
accepted decisions update the affected comparison, and publication proposes only
remaining owner actions. An old broad investigation proposal produces no repeat
assignment when its evidence is already available. A genuine inaccessible proof
produces a specific evidence request with the access limitation.
