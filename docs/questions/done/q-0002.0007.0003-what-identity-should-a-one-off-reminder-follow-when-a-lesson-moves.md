# q-0002.0007.0003 What identity should a one-off reminder follow when a lesson moves?

Decision: the user, 2026-10-04, accepted following the same lesson occurrence
through a scheduled date or time change, without creating a recurring subscription.
The [reminder-selection contract](../../boundaries.md#accepted-reminder-selections)
owns the agreement. The user asked to compare it with Cabinet frontend and use
that frontend as a reference.

Source evidence inspected on 2026-10-04: Cabinet's
`api/src/lessons/lessons.service.ts` updates a lesson by its existing `_id`, including
changes to `startsAt`; its planner test preserves the same lesson ID for a manual
reschedule. Daychi's `attendance.ts` stores one-off choices by occurrence ID,
and derives a series ID by removing the date suffix. Inspected source revisions
are recorded in [current-system.md](../../current-system.md).

Boundary scenario: a selected Tuesday lesson moves to Wednesday. Following the
lesson preserves the selection for that one rescheduled occurrence; following the
original date requires a new choice for Wednesday. The recommendation is to
follow the same lesson, without converting the choice into a recurring subscription.
Cabinet frontend recheck: `LessonScopeClassList.tsx` and `lessonScopeEdit.ts`
select by class ID; `useLessonScope.ts` reads and writes account scope and lead
time. `StudentLessonsScreen.tsx` identifies lessons by ID. The backend reminder
planner uses the lesson's current start time and class scope. Cabinet does not
currently expose a one-off lesson-selection field. The accepted rule matches its
stable identity principle and extends its existing capability; it is not a claim
that the one-off feature already exists. Presentation remains project-owned.

The current frontend/API behavior is the reference for preserving Cabinet's
consumer obligations. Exact identifier encoding and implementation remain under
the parent migration question; the identity behavior here is settled.
