## Local tickets as reconciliation deliverables — accepted 2026-10-05

The user proposed feeding reconciliation work records through /ticket, creating
local tickets whose outcomes can include published project issues, and accepted
landing this method. No concrete work breakdown was approved or tickets minted.

The accepted distinction is between three records: the reconciliation report holds
evidence and remaining findings; a local ticket holds Workshop's work to resolve
and deliver an outcome; a resulting GitHub issue holds the recipient project's
assigned work. One Workshop outcome may yield several coordinated project issues,
an accepted record change, or a justified disposition requiring no external issue.
These are different deliverables, not two copies of the same implementation task.

A ticket explicitly scoped to an agreed, verified and published handoff can finish
when that outcome is verified. A ticket scoped to a working cross-project boundary
cannot finish merely because an issue was posted. Project execution and Workshop's
later acceptance remain visible in the addressed issue and reconciliation state.
Recorded evidence is input to the invoked skills; it supplies no workflow authority.

### Impact

This adds a durable delivery record for Workshop's remaining reconciliation work
between comparison and external publication. Existing /ticket shaping, /impact,
approval and verification can govern those outcomes. The outgoing tracker and
recipient implementation ownership remain the same.

### Hidden edges

A local wrapper per external issue would duplicate tracking without correcting
work selection. Splitting by record row, process stage or recipient can fragment
one shared outcome. The existing evidence and accepted decisions are the starting
point; local tickets cannot justify repeating completed investigation. Publication
alone proves only a handoff, not the recipient's implementation or deployed behavior.

### Leave alone

Completed collection, accepted boundary contracts, recipient ownership, current
issue-return channels and the distinction between Planned publication and execution
release. Routine factual corrections and follow-up within an existing assignment
need not acquire an additional local ticket solely for this process.

### Recommendation

Proceed with local tickets for reconciliation work that needs shaping, decisions
or a distinct verified deliverable. Published project issues can be outputs of
those tickets. Direct publication from an already-shaped finding is the lighter
alternative, with less durable visibility of Workshop's preparation and acceptance.
The user accepted this default and its exceptions. P12 now owns the instruction

resolution and verifies publication against the local outcome. No new ticket kind
or status was introduced.
