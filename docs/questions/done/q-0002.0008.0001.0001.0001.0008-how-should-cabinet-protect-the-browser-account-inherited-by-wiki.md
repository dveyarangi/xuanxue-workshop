The customer is the person signed into Cabinet who expects wiki to inherit that

The reviewed source supplies a conditional cookie-selection counterexample. Its

## Source and controlled witness

At Cabinet `67d5cbd0041daa13c6973b657479e45a6716486f`,
[session-cookie.ts](https://github.com/gregoryKot/xuanxue-cabinet/blob/67d5cbd0041daa13c6973b657479e45a6716486f/api/src/auth/session-cookie.ts)
names the account cookie `session`, creates a host-only HttpOnly/Lax cookie and
uses a first-matching-name parser. It does not reject duplicate `session` values.
The same source's clear helper emits Secure=false, which cannot simply be reused
unchanged if the name acquires a protected prefix.
[session-user.ts](https://github.com/gregoryKot/xuanxue-cabinet/blob/67d5cbd0041daa13c6973b657479e45a6716486f/api/src/auth/session-user.ts#L14-L24)
selects that cookie before verifying the token and loading the account.
[Native browser completion](https://github.com/gregoryKot/xuanxue-cabinet/blob/67d5cbd0041daa13c6973b657479e45a6716486f/api/src/native-auth/native-browser-flow.service.ts#L118-L135)
already uses this helper; the proposed web adapter was to reuse the same authority.

The original session-cookie module was executed locally under Node 24.14.1 with
only TypeScript annotations stripped. With illustrative values, the exact parser
returned `attacker-valid-session` for
`session=attacker-valid-session; session=legitimate-session`, and reversed the
result when the values' order was reversed. This executes cookie selection only:
it is not a test of signatures, a browser exploit or a live production attack.

The standards-derived counterexample additionally assumes control of a sibling
HTTPS subdomain and the attacker's own valid Cabinet session A. A parent-domain
`session` cookie scoped to `/auth/wiki` can appear ahead of the legitimate host
cookie B on the wiki authorization path. Cabinet's existing parser selects A;
its signature is genuine, so verification does not restore B. Cabinet's root
page can still use B while the handoff returns A. Correct state/S256 binds the
victim's own attempt to that incorrectly selected account; the backend secret
authenticates Daychi, not the account-cookie's browser origin.

[RFC 6265 §§4.2.2 and 5.4](https://www.rfc-editor.org/rfc/rfc6265.html#section-4.2.2)
explains same-name ambiguity, absent attributes in Cookie headers and path ordering.
[MDN cookie prefixes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#cookie_prefixes)
describes the host/path/HTTP protections of `__Host-Http-`; browser prefix support
is required for those protections. No claim is made that any sibling is currently
compromised or that a production user's identity was changed.

## Historical hardening option — not adopted


On HTTPS issuers, Cabinet's account and authorization-binding cookies use
`__Host-Http-` names with Secure, HttpOnly, Path=/ and no Domain. Cookie selection
rejects duplicate expected names; issuing, rolling renewal and clearing use the
same protected name and valid prefix attributes. The existing account/login
methods, HMAC session representation and account ownership remain intact.

After migration, an unprefixed `session` cookie does not authenticate a protected
browser flow or silently convert into a trusted prefixed cookie. Existing legacy
Cabinet browser sessions require one fresh sign-in through the existing methods;
subsequent wiki handoffs reuse the new valid browser session without another
password/confirmation. Native bearer grants and other already-issued client grants
are not revoked by this cookie-name migration. HTTPS fixture/staging behavior
exercises the protected cookie; non-HTTPS development remains outside this web
profile's deployment tuples and cannot relax production protection.

Cabinet owns the implementation and rollout; Workshop coordinates the changed
browser compatibility promise. Shared proof includes two valid fixture accounts,
a controlled sibling origin, a longer-path parent cookie, duplicate protected
names, failed legacy fallback, successful new sign-in/automatic handoff and actual
logout expiry. It also preserves native bearer/self-profile and existing login
methods while explicitly recording the one-time browser reauthentication.

Keeping legacy fallback would preserve its untrusted origin ambiguity. Hardening
only wiki cookies does not protect Cabinet's selected account. Replacing the
browser account source with a new identity system is unnecessary: a protected
cookie namespace and explicit migration suffice for this counterexample. The
tradeoff of this option is one fresh Cabinet browser login per old browser
installation. It changes an accepted compatibility expectation, so it is not
landed as an accepted rule and no recipient source is modified.

## Necessity correction after user challenge — 2026-10-12

The user challenged the assumption that an attacker could control a school
subdomain, then asked whether the existing cookie can authenticate the user.
The answer is yes: Cabinet already selects the cookie, verifies its signed
session and loads the account. The web handoff can reuse that existing browser
authentication. The host-only Cabinet cookie is sent to Cabinet; wiki receives
the resulting authorization code and establishes its own local cookie session.
The Cabinet cookie is not made available to wiki or widened to the parent domain.

The earlier mandatory-migration conclusion and its acceptance blocker are
withdrawn. The executed parser witness and conditional counterexample remain
accurately bounded evidence. A trust-boundary/hardening decision may be considered
separately if deployment evidence or an accepted threat model makes sibling-origin
control relevant; it does not by itself block this web profile. No new browser
logout or one-time reauthentication requirement has been accepted.

## Disposition — 2026-10-12

The accepted [shared browser session](../../contracts/web-wiki-session.md#accepted-shared-browser-session)
treats the school domain/subdomains as one trusted session namespace and reuses
Cabinet's existing cookie. A mandatory host-prefixed migration is not needed for
this accepted shape; that option would prevent the accepted Domain sharing.
The original source witness remains bounded evidence. This profile question is
moot, with no claim of a compromised subdomain or authorization to change
recipient source for the discarded option.
