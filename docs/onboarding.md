# Project onboarding

Onboarding establishes the context of a project's participation and a verified
connection between its agent and Workshop. It is available to a project unknown
to Workshop, independently of whether assignments exist.

## Entry and project reception

The Workshop README and [/collaborate](../skills/collaborate/SKILL.md) are the
canonical entry. The project's original issue owns its connection context:
an existing introduction or installation issue, or a new project introduction.
The author of a first request need not assign a recipient label. Workshop owns
discovery and classification of that request.

The context includes the repository, purpose, accountable operator, participating
GitHub accounts, agent host and known cross-project connections. Unknown facts
remain open questions. An existing installation and its provenance inform the
work required for the connection.

## Access and communication

The Workshop repository owner is responsible for access grants. The project's
operator owns authorization of the connection in its environment and local
installation. Shared obligations and acceptance conditions follow the
[agent interaction contract](agent-contract.md#entry-and-first-assignment).

## Installation source

Workshop supplies one published revision of /collaborate and its companion
[issue format](../skills/collaborate/workshop-issue-format.md). That revision
identifies the source of both retained instruction files.

## Boundary context

Workshop supplies the agreed project label and boundary summary as part of the
connection context. The summary identifies responsibilities, governing contracts
and local entry points, distinguishing existing connections from targets. Detailed
shared promises remain in their authoritative contracts.

## Collaboration installation

Connection acceptance establishes retained instructions and their source revision,
their use in a fresh session, Workshop access, addressed-work search and a working
reply path. An empty search result is valid. Evidence, disclosed limitations and
the review outcome remain in the original issue; a separate installation issue
is not required.

Connection acceptance and eligibility for project work are independent outcomes.
Eligibility depends on the operator's authority and the actual dependencies of
the activity. Acceptance of the connection does not establish readiness of
application integrations.
