## Scope

The [accepted web handoff](../../boundaries.md#accepted-web-wiki-sign-in-handoff)
places code exchange and Cabinet-held user authority behind Daychi's web backend.
The [accepted lifetime policy](../../boundaries.md#accepted-web-wiki-lifetime-and-renewal)
requires backend renewal. Cabinet binds these operations and session/account
validation to an authenticated consumer under the accepted answer below; caller
trust is not supplied by a reader's browser cookie or the native registration.

## Existing constraints and references

Cabinet remains the account and admission authority. Authenticating the calling
service cannot substitute for validating the reader's credential, account and
authorized use. The shared admission wire remains part of the broader
[credential question](../q-0002.0008.0001-how-will-daychi-clients-obtain-and-present-cabinet-credentials.md).

[RFC 6749 client authentication](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.3)
defines confidential-client credentials, including client-password HTTP Basic
authentication over TLS. [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.1)
requires authorization for token introspection. These establish available protocol
mechanisms, not adoption of introspection or full OAuth/OIDC. The accepted answer
below selects client_secret_basic. Exact registration values, rotation behavior
and operation bindings remain in the parent web-profile question.

PKCE binds an authorization attempt and is not proof of the calling service's

recommends client authentication where confidential credential provisioning is
feasible. [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.1)
requires authorized introspection and permits different authorization mechanisms.
Neither reference establishes that client_secret_basic is this project's only
option, nor that reader credentials automatically authenticate a confidential
client. The exact endpoint roles, consumer bindings and caller trust remain open.
No no-secret web profile or replacement authentication method was accepted by
this challenge; accepted handoff, explicit exit and lifetime policy remain fixed.

## Families

These families match different relationships in the subject and can coexist. Each “ladder” below describes increasing commitments, not a universal maturity ranking.

1. **Authorization-code handoff.** Ladder: browser-mediated return → short-lived one-use code → transaction-bound exchange → separately authenticated client and constrained issued credential. The subject occupies the transaction-bound rung: callback, state and S256 connect an exchange to its initiating attempt. This protects the handoff; it does not establish continuing account validity or prove the application’s registered identity. Failure modes include state accepted without binding to the initiating browser, verifier reuse or exposure, non-atomic code consumption, redirect weaknesses and PKCE downgrade. Current OAuth guidance requires transaction-specific PKCE securely bound to the client and initiating user agent, and exact redirect matching. **Confidence: high** in this structural match and the distinction; implementation correctness is unknown. [RFC 9700 §§2.1–2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1)

2. **Federated sign-in.** Ladder: local accounts → central account authority with application-local sessions → standardized identity assertions → federation across multiple authorities. The subject sits at central authority with local sessions; its transport resembles OAuth’s code flow, but no ID Token or other OIDC identity contract was specified. OIDC adds an explicit authentication result with issuer, subject and audience validation. Consequently, recognizing an account through a defined current-account endpoint could match the federation relationship without establishing OIDC compliance. Failure modes include confusing a credential’s existence with authenticated identity, linking accounts by mutable email, and accepting an assertion intended for another application. “Same account” also need not mean identical identifiers across applications: OIDC permits pairwise subjects. **Confidence: high** in the relationship; **medium** in the precise classification without the identity contract. [OpenID Connect Core §§2, 3.1.3.7, 8](https://openid.net/specs/openid-connect-core-1_0.html)

3. **Server-mediated browser sessions.** Ladder: credentials exposed to browser code → backend obtains credentials but returns tokens to browser → backend retains credentials and browser receives a local session cookie. The subject sits at the final rung. It matches the token-custody aspect of a Backend for Frontend; a complete BFF classification additionally requires the relevant protected API traffic to pass through that backend. A content-serving backend need not introduce a separate proxy merely to resemble the pattern. Failure modes include local session fixation, cross-site request forgery, backend credential leakage and malicious JavaScript making authenticated requests through the browser. HttpOnly limits direct cookie access; it does not stop that last behavior. **Confidence: high** for server custody; **medium** for “BFF” as the complete architectural label. [RFC 10017 §§5.1.4, 6.1](https://www.ietf.org/ietf-ftp/rfc/rfc10017.html)

4. **Reference credentials with authoritative validation.** Ladder: local cached login fact → periodically revalidated credential → authoritative validation on protected requests → explicit freshness and failure guarantees. The opaque revocable credential plus current-account validation places the subject somewhere beyond a cached login fact; validation frequency remains unstated. OAuth token introspection is a structurally matching standard alternative, not proof that the existing endpoint implements it. Revocation takes effect at the consumer only when observed. Caching introduces a freshness window; checking every request introduces availability and latency dependencies. Renewal does not itself prove that the account remains eligible unless the authority checks that condition. Failure modes include serving from a stale local cookie, treating network failure as success, and inconsistent logout across sessions. **Confidence: high** in these dependencies; **low** in the actual revocation guarantee without timing semantics. [RFC 7662 §§2, 4](https://www.rfc-editor.org/rfc/rfc7662.html)

5. **Application authentication and credential possession.** Ladder: claimed application identifier → registered identifier and callbacks → authenticated confidential client → issued credentials additionally bound to a sender. The task specifies registration-like binding, not application authentication. A `client_id` is public and cannot authenticate the client alone. PKCE proves possession of an attempt-specific verifier, not possession of the application’s registered secret or private key. Separately, authenticating a backend during exchange does not automatically make its issued user credential resistant to theft and replay. Failure modes include mistaking callback registration for backend authentication, exposing client secrets to frontend code, and accepting stolen bearer credentials. **Confidence: high** in all three distinctions. [RFC 6749 §§2.2–2.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.2), [RFC 9700 §§2.2, 2.5](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2)

## What the tasking smuggled in

- Existing provider login survives the visit and may be reused; “without another password” does not guarantee no redirect, consent or renewed authentication.
- The second backend is trusted to hold user credentials and can protect server secrets.
- An authenticated account is sufficient for content admission; account suspension, deletion, expiry and revocation still need definitions.
- “Same account” has a stable authoritative identity contract.
- Code binding is enforced during exchange, including atomic single use.
- Renewal and logout have compatible meanings across provider credentials and local cookies.
- All protected delivery paths—including downloads, caches and direct backend routes—obey the admission condition.

**Confidence: high** that these are necessary unanswered assumptions; their truth was not established.

## Nothing to take

No individual family proves the entire arrangement sufficient. Transaction binding, continuing user validity and application authentication answer different questions.

Generic analogies to microservices, RBAC or “zero trust” add no matching structure here. Neither identical content nor opaque credentials establishes a need for roles, JWTs, shared browser cookies or a full OIDC implementation.

## Source-backed caller-authentication recommendation — 2026-10-12

The inspected native profile is a public-client profile, with no client secret.
Its code exchange has transaction binding, not independent caller authentication.
The accepted web model instead has a server obtaining and retaining credentials
and accepting browser requests through its own session. Daychi already protects
server-only owner configuration and supplies HTTPS/Origin/CSRF support in
[admin.py](https://github.com/sleontenko/daychi/blob/d2cde6b93ef79734e4de0438ddc2e138698214af/practice_api/admin.py).
That establishes the existence of server configuration, not deployment of a wiki
application credential or authorization to provision one.

[RFC 10017 §6.1.3.1](https://www.ietf.org/ietf-ftp/rfc/rfc10017.html#section-6.1.3.1)
requires confidential-client credentials for its backend-mediated architecture.
[RFC 9700 §2.5](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.5)
recommends client authentication where confidential provisioning is feasible,
with an asymmetric preference. PKCE remains transaction-specific protection.
This is a concrete basis for application authentication in the chosen web model,
rather than an extra wiki-reader entitlement.

The recommendation presented to the user was a confidential wiki consumer in Cabinet's
shared authorization core, with a separate high-entropy client secret per issuer
environment and client_secret_basic over HTTPS. The secret authenticates the
application during code exchange and the specified server lifecycle calls;
the reader credential and current account are validated separately. Secret
possession alone authorizes no user's wiki session and no staff, import or
arbitrary-account operation. The application secret stays in operator-controlled
server configuration; it is absent from browser code, URLs, logs and user cookies.
Cabinet and Daychi operators own provisioning and rotation of their ends.

Existing native registration remains public and its wire unchanged. Shared
authorization, random credentials, hashing, account validation, renewal and
revocation stay in one core with explicit expected-consumer checks. This is a
consumer registration and a caller-authentication addition, not another account
store or user sign-in method. There is no new wiki-reader role or eligibility
scope. Account/session validation is limited to the presented user's own grant,
rather than a general-purpose token-inspection service.

Static shared-secret client authentication is narrower to integrate than adding
certificate or signed-assertion infrastructure to this inspected tree. Asymmetric
authentication remains the standards-preferred alternative, with additional key
registration/verification work. A deliberately unauthenticated server consumer
would retain code/PKCE protection but weaken application authentication relative
to the cited backend-client standard; callback registration alone cannot be
represented as authenticating that server. The recommendation was accepted below;
the exact web operations remain open in the parent question.

The user's earlier challenge withdrew an unsupported presumption, not every
possible application-authentication method. This evidence-backed recommendation
does not reopen accepted reader access, handoff, local exit or lifetime policy.
