The user then asked whether the proposed shape fits existing endpoints and what
the authenticated endpoint actually provides. Source inspection confirms:

- `GET /api/me/lessons?limit=...` maps to `GET /me/lessons` in Cabinet's shared
  route map; the application setup supplies the `/api` prefix.
- Query is `ListMyLessonsQuery`, with optional integer limit 1–50 and default 10.
  This endpoint has no date-window query.
- Authentication uses the `session` cookie. The global guard verifies session and
  current user; no route-specific staff role is required. Native bearer support
  remains an unimplemented target.
- Success is `MyLessonDto[]`, with future lessons sorted by start, including
  cancelled future lessons. The route reads the school's upcoming lessons, not
  the caller's reminder choices. It includes optional effective Zoom fields.
- Lesson fields use Cabinet's camelCase types. Existing student and staff list
  endpoints return bare arrays. Cabinet's route map permits the additional public
  route, but its query and response require new typed definitions and registration.

The earlier draft envelope added an unnecessary difference. The user accepted
the existing array and item shape without Zoom, then explicitly accepted adding
`classId` to each item. The user's suggested route spelling is
`GET /api/public/lessons`. The [target record](../../boundaries.md#accepted-first-schedule-connection)
holds these decisions. Exact public fields are allowlisted rather than inherited
by excluding only today's private fields.

The user's question about a separate class-ID list concerns a different structure:
Cabinet's existing `LessonScope.classIds` records a user's recurring notification
choices. Each schedule occurrence's `classId` links it to its class. Several
occurrences may therefore share one class ID while each has its own lesson ID.
The public pilot has no separate class-ID list or reminder-settings operation.

### Source-derived constraints

Daychi's `schedule/source.ts` and `practice_api/schedule_source.py` generate today
and the following thirteen school calendar dates in `Asia/Jerusalem`, including
earlier events on today's date. The accepted requirement to support that existing
coverage is the starting point, not a new rolling-336-hour requirement. Cabinet's
`lessons.queries.ts` already selects starts with `from <= startsAt < to` for its
staff window route; it is reusable prior art, not existing support on the student
or public schedule route. Both sources use offset-aware instants.

The current student route is protected and count-limited. Its shared DTO and mapper
include Zoom fields and omit class identity. Daychi's normal schedule loader and
decoder are tied to the school template, and normal refresh mutates reminder state.
The pilot must adapt these shared data assumptions without replacing the ordinary
flow. Executable definitions remain authored in Cabinet; internal client structure
and presentation remain Daychi's.

Source facts for the accepted student-field shape: Cabinet's mapper encodes the
existing lesson ID with `_id.toString()` and emits UTC ISO `startsAt` with `Z`.
Its class relationship is an ObjectId encoded as a string. The client does not
derive identity from dates. `durationMin` is minutes; `format` values are `online`,
`offline`, `both`; `status` values are `scheduled`, `cancelled`. `classTitle`,
`groupLabel` and `topic` are strings; `tags` is a string array, with absent legacy
tags mapped to `[]`. `location` is optional and omitted from JSON when absent.
These are source-derived meanings of the accepted fields, not new user choices.
