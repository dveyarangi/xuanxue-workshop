Ownership is settled in [architecture](../architecture.md), by the user on
2026-10-03. This question concerns migration and interoperability, not whether
Cabinet should own these capabilities.

Evidence and unresolved choices:

- Schedule: Cabinet's student endpoint is authenticated and returns a limited
  upcoming list, including optional Zoom credentials. Daychi currently has a
  public fourteen-day view. Determine the public/private projection and date-window
  contract without exposing protected meeting data. Map Daychi's derived series
  and occurrence IDs to Cabinet classes/lessons so saved choices remain meaningful.
- Users: determine how existing Daychi access is associated with Cabinet users,
  how native clients authenticate, and how the retained Daychi content backend
  verifies access and revocation. Current cookie and bearer implementations are
  different; neither supplies this integration merely by changing the base URL.
- Reminders: Cabinet supports selected classes and lead times 15/30/60/120 minutes
  with a school default. Daychi supports individual dates, recurring selections,
  skips, and lead times 0/15/30/60 with device-local delivery. Define preservation
  or deliberate migration of these semantics and the native/offline delivery
  contract, including preventing duplicate local and server notifications.
